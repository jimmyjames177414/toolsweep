# The Peridot CRM example

**Everything in this folder is invented.** Peridot is not a real company, none of the
tools exist, and every id, email address and company name was made up for this example.
Email addresses use the reserved `.example` domain.

| File | What it is |
|---|---|
| `catalogue.json` | 20 tools, MCP `tools/list` shape, with toolsweep's `x-toolsweep` extension block |
| `suite.jsonl` | 40 tasks covering 14 of those 20 tools |
| `cassette.json` | Recorded responses for one demo command. **Synthetic** — generated by the mock, not captured from a model |
| `make_cassette.py` | Regenerates the cassette |

## What is deliberately wrong with the catalogue

A clean catalogue would demonstrate nothing. This one is built with the flaws the factors
exist to measure:

- **Two clusters of near-synonym retrieval names.** `get_customer` / `lookup_customer` /
  `find_customer` / `search_customer`, and `get_invoice` / `list_invoices` /
  `find_invoice`. Every one is valid; each pair differs only by a synonym of the same verb.
- **Raw enum codes with human labels beside them** — `ACT` / `INACT` / `PEND` / `CHURN`,
  labelled `active` / `inactive` / … — so `enum.wording` has both forms to swap between.
- **A flat filter group.** `search_customer` takes `filter_status` and `filter_region` as
  top-level arguments, which `schema.nesting` can group into an object.
- **A required list that overstates itself.** `create_invoice` marks `currency` required but
  flags it `essential: false`; `void_invoice` does the same for `reason`. Without that
  distinction, `params.required=minimal_required` would have nothing to say — and toolsweep
  would report it as inert rather than pretending to measure it.

## Why the suite covers only 14 of 20 tools

The last six tools — `get_pipeline_stage` onwards — are never expected by any task. That is
on purpose, and it mirrors reality: a real server exposes more tools than any one suite
exercises.

It also makes `catalogue.size` measurable. That factor never drops a tool the suite expects,
so on a catalogue where every tool is expected there is no valid subset and the factor has
nothing to vary. toolsweep reports that as **not measurable here**, with the reason, rather
than silently omitting the factor — but a demo that could not show one of its eight factors
would be a worse demo.

## Why the prompts are worded the way they are

Each prompt names the field that distinguishes the right tool: "customer id CUS-1041",
"email address dana.okafor@…", "company name Vantage Loom", "status PEND and region APAC".

That is because the demo's default provider is a **lexical** mock. It picks tools by word
overlap between the prompt and the tool's name, description and parameter names. A suite
full of oblique phrasing would leave it guessing at random, and the sweep would measure
noise rather than the effect planted in it. Against a real model, prompts can and should be
as natural as your users' actual requests.

## Regenerating the cassette

```bash
python examples/crm/make_cassette.py
```

The cassette is keyed by a hash of the whole request, so it only replays the one command it
was recorded for:

```bash
toolsweep sweep examples/crm/catalogue.json examples/crm/suite.jsonl \
    --factors naming.synonyms,description.negative \
    --provider cassette --cassette examples/crm/cassette.json --repeats 3 --seed 7
```

Change `--repeats`, `--seed` or `--factors` and the keys change; the cassette provider
raises rather than quietly falling back to a live call, because a run whose numbers came
half from a recording and half from a model is not a run.

It covers this narrower command rather than the README's headline `--factors all` sweep
because a full-grid cassette at five repeats is 2,800 entries and 1.2 MB. The mock
reproduces the headline table offline for free, so committing that much JSON would buy
nothing.
